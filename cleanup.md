# Cleanup scout: current working tree

**2026-09-29 decision update:** The earlier fixed `0.7` Jev policy below is
superseded. The caller supplies one `DecisionConfig.threshold` per `Lexicon`
instance (or `LEXI_DECISION_THRESHOLD` via `from_settings`). The same
inclusive boundary applies to Noul yes-probabilities, applicable Jev Choice
confidence/fallback, and grading's Noul outcomes. The lexical fuzzy-search
similarity score is unrelated. No decision threshold is hard-coded in v2.

This document records a read-only assessment of the **current, uncommitted working tree**, subsequent product decisions and the selected target project structure. It is not a review of a fixed commit. The project is undergoing a large refactor; deleted files were not counted as dead code. Scout findings are candidates for discussion; decisions and the target structure are direction for future implementation, **not changes already made**. Later decisions below supersede older cautions about preserving generated databases and external consumers.

## Polish/publication scope and settled product decisions

- **Outcome:** Reduce unnecessary code, duplication, wasteful work, and overengineering; make the library clear and production-ready before making the repository public on GitHub. Do not add capabilities merely to make the architecture look complete. This is not a PyPI-release decision.
- **Compatibility:** Breaking changes are allowed; there are no downstream consumers or generated-dictionary databases to preserve. Do not maintain legacy code, public API aliases, or compatibility migrations solely for old releases. This does **not** make input tolerance from current Cambridge/WordNet/model outputs automatically obsolete.
- **Migrations:** Squash the generated dictionary's Alembic history into one baseline for the final schema; retain schema features such as the `senses.word_id` index. Verify a fresh Postgres upgrade, schema drift check, downgrade/re-upgrade, and non-default-schema SQL. The separate, read-only Cambridge reference DB must remain untouched.
- **Search-selected generation — final product contract:** The consumer first calls the **one public search** below and offers a request action only on an available result. Public `generate(available_id, style=None)` accepts that result's opaque, source-neutral handle, which resolves internally to a **selected Cambridge entry ID**; it does not accept arbitrary text, choose between references, or search again. If that entry ID is already associated with a Word whose `generation_state="done"`, reuse that Word without regenerating neutral content. Otherwise fetch the entry **by ID**, use Cambridge as the primary lexical source and WordNet only as optional supporting evidence, and generate one neutral Word. With `style=None`, return the neutral Word. With a requested Style, ensure neutral exists first, then generate that Word's styled definitions/examples **only if absent**; otherwise return its existing styled view without an LLM call. The Style-specific generation is not Word regeneration and never generates Questions. A missing/invalid handle, missing/broken Cambridge DB, provider failure or invalid model output is an error, not an invented Word or an `explanation` branch. The consumer owns when to show/request the action and coordination across simultaneous calls; the read-only Cambridge DB stays untouched. This replaces the earlier Cambridge-first free-text path, manual reference selection, WordNet-only/custom generation, and public `force` regeneration of an already-done selected entry. See the full Style lifecycle and schema below.
- **Concurrency ownership — decided:** Lexi-AI is a library, not the distributed scheduler. The consumer owns serialization, deduplication, and ordering of simultaneous *operations* (including Word/Style generation, Question generation, translation-cache writes and maintenance on the same resources). Remove library-owned cross-call coordination mechanisms: generation/Style `SingleFlight` locks, `generate_fenced()` and claim/epoch/stale-publish code, and old Asset file-write-vs-GC locks/listeners (the file-backed TTS capability itself is now removed). Do not silently replace them with another library lock/queue. Keep correctness within one call: transactional publish/rollback and database uniqueness/foreign keys are not distributed-work coordination. State the caller's concurrency responsibility prominently in the public contract; no guarantee that simultaneous calls deduplicate LLM spend or resolve conflicting writes. **Explicit exception:** one `resolve_relations(batch_size)` call parallelizes its independently selected links internally; that is per-call work execution, not a lock/queue coordinating different consumers.
- **Batch convenience API — decided:** Remove the convenience wrappers `generate_many`, `get_many`, `get_status_many`, and `translate_many`, plus `gather_batch`, internal parallel execution/limits and their `concurrency` knobs. `tts_many` goes away **with all of TTS**, not as a retained single-item TTS feature. Consumers call retained single-item methods and own batching, retries, error isolation and parallelism. This does **not** change per-item provider usage: reads and cache hits remain provider-free; a miss may invoke the relevant provider. Keep genuine batched DB reads such as `get_senses(ids)`; WSD judging is separately being redesigned per relation below, so do not preserve its old batched LLM call on this basis. Re-evaluate `BatchResult` after tracing remaining uses. Update public-surface tests, examples/docs and stale comments rather than retaining aliases. `generate_questions(..., count)` remains a distinct one-request LLM batch operation, **not** a wrapper that loops over single-question generation.
- **Management APIs — decided:** Remove `Lexicon.source_hash()` and its dedicated service forwarding, which exist to fence a delayed external translation job; revisit any reusable source-hash primitive only if a real non-coordination use remains. Keep **Style**/topic (currently named tag in code)/retained translation-cache management APIs when those capabilities are retained: consumers need to inspect, update or delete resources they create and inspect/prune cached translations. `Theme` is the old implementation name for Style, not a second product concept. Do not equate lack of example calls with uselessness. **No file-backed TTS remains**, so its file orphan sweep, binary-asset maintenance and related coordination are not part of the target.
- **Sense-relation resolution — decided:** Keep sense-level WSD as an **explicit, optional consumer-triggered job**, runnable manually or by a consumer-owned worker. Remove the implicit `generate()` → `resolve_inbound()` hook and its special inbound factor/filter/wiring: generating a word must not secretly spend a judge request after publication. Generation still writes sense→target-word half-edges; they remain `pending` until their target word has senses and the consumer runs resolution. Keep `resolve_relations(batch_size=20)` (and its sensible cap): select up to `batch_size` eligible pending links in deterministic order and process independent links **in parallel** within that call, with separate per-link Jev requests and at most one per-link LLM fallback request. Do not batch links into one model request. **Strict POS policy:** only target senses with the *same* part of speech as the source sense are candidates; remove the current `pos_filtered_candidates()` fallback that reintroduces different-POS senses when there is no same-POS match. With no eligible candidates, code decides `0` without either model call. Missing/invalid POS is an input/data error, not permission to consider all senses. Preserve per-link result/error isolation and validate that a model's chosen index is in range. The consumer still owns scheduling and coordination of overlapping `resolve_relations()` invocations; no in-library job queue or cross-call lock.
- **Remove `see_also` entirely — decided:** This loose sense-relation type is the explicit example used to justify the cross-POS WSD fallback (`run` verb → `marathon` noun in `tests/test_resolve.py`), but removing it alone does not remove that generic fallback: enforce strict POS independently. Remove `see_also` from `REL_TYPES`/`REL_LEVEL` and generated schema vocab in `lexi_ai/vocab.py`, the generation prompt, WSD prompt/comments, schema descriptions, tests and examples; do not keep a compatibility alias or migration for old generated rows (none exist). Retain the other deliberate sense-level relation types and word-level `word_family` as currently scoped.
- **Jev WSD input — decided:** One relation per Jev classification request. Use a structured JSON object for `state`, not the previously agreed multiline string:

  ```json
  {
    "task": "Word Sense Disambiguation",
    "source_word": "{source_word}",
    "source_definition": "{source_definition}",
    "relation_type": "{relation_type}",
    "source_pos": "{source_pos}",
    "target_word": "{target_word}",
    "target_gloss": "{target_gloss}"
  }
  ```

  `target_gloss` is the generated relation's hint about the intended target meaning, **not** an already-resolved DB sense. POS appears once, from the source sense. Keep reusable Choice question ID `wsd` with the exact static instruction `Which candidate sense of the target best matches the target sense described in the state?`. Dynamic criteria use string keys `"0"` = no candidate matches, `"1"`, `"2"`, ... = the **candidate senses in the chosen candidate-list order**, each represented by its relevant definition(s). That numeric order is transient WSD candidate ordering, **not** a stored order for the several definitions of one sense. Map the chosen number to the persisted sense ID in code, never by asking the model for an ID.
- **Jev-first cascade — decided:** Use **0.7 for every Jev threshold**, including WSD Choice confidence: if confidence is **below 0.7**, fall back through the **shared decision-model adapter** for this relation; at or above 0.7, accept Jev's choice. Both backends select one number `0..N`; `0` means no candidate matches, and `1..N` maps to the corresponding target sense. No separate `match`/`no_match`/`uncertain` model output; accept the valid fallback result as final. Code determines `0` directly when strict POS filtering leaves no candidates. The read-model `unresolvable` state is derived in code from a completed `0` decision; when candidates exist, code cannot know semantic non-match without a model verdict. Transport/validation failure is an error rather than a model decision. Do not add a WSD-specific handwritten LLM fallback request.
- **Non-goals for this brainstorm:** No implementation yet; do not flatten useful transaction boundaries or remove safety invariants merely to reduce line count.

### Word generation — settled product contract

- **Terminology, input and cardinality:** In the redesigned Lexi-AI model, call the generated object a **Word**; reserve **entry** for Cambridge internally. One selected Cambridge entry ID produces **exactly one Word** with as many senses as appropriate; there is **no `explanation` variant, free-text generation or `GeneratedResult.units[]`**. If generation cannot produce a valid Word, fail rather than publish fabricated or partial content. Do not automatically generate other independent idioms/phrases mentioned by the selected Cambridge page. The old code's `Entry`/`GeneratedEntry`/`units` names are implementation history, not the target output or public vocabulary.
- **Word fields:** `lemma`, `entry_type`, `aliases[]`, `topics[]`, `new_topics[]`, `related[]`, `senses[]`. Rename the current `norm` field to `lemma` for the canonical word or multiword expression; a normalized lookup key remains an internal derived value, not the lemma itself. Remove word-level `pos` from generated output, storage and read model: POS belongs to each sense; a word can span POS. Preserve alias identity and the retained entry-type vocabulary unless separately reconsidered.
- **Canonical multiword lemma and identity — decided:** Require the LLM to produce one stable **dictionary citation** as `lemma`, for the generated Word **and** every target lemma in its word- and sense-level relations. For `phrasal_verb`, use the base verb plus **all fixed particles/prepositions** without subjects, objects, tense or argument slots: `take off`, `put up with`, `look up to` (`look up` is a different lemma). Inflection, separable word order and object positions belong to sense-level `patterns[]`, not the phrasal-verb lemma. For idioms/phrases/expressions, retain fixed articles, negation, contractions, prepositions and meaningful punctuation; if deleting a variable constituent would break or change the conventional headword, use a **canonical typed placeholder** in its position: `the apple of {one's} eye`, not `the apple of eye` or an inconsistent literal `someone's`. A fully fixed idiom needs no placeholder. Never put Cambridge slash alternatives, parentheses/optional notation, `etc.`, a contextual inflection, or a paraphrase in the canonical lemma. Use the **selected Cambridge entry** as the citation anchor, converting its display notation to this contract rather than copying it verbatim; WordNet may enrich senses but does not supply a different generation target. The generator must apply the **same instructions to relation targets** rather than emitting a usage pattern as the target lemma. Validate allowed tokens and normalization in code rather than trusting the prompt alone.
- **One identity field plus derived lookup key — decided:** `lemma` is the Word's lexical identity; keep the existing idea of code-derived `match_key` for indexed/equivalent lookup and uniqueness, **not** a second LLM-generated `lemma_key` or separate product field. Normalize both stored lemma and relation target by the same safe rules (Unicode, case, whitespace and canonical typed placeholders); preserve fixed particles, articles, apostrophes, hyphens, diacritics and literal slashes. Distinguish literal `someone`/`something` from a marked slot; do not globally delete or replace these words just because they look like placeholders. Relation-to-Word identity resolution is **lemma-based only** under the accepted simplicity trade-off: aliases, inflected forms and patterns support search/usage, but do not auto-merge two differently named Word rows or prove a relation target is the same Word. A mismatch in two independent LLMs' citation choices may therefore create duplicate Word/stub rows; no guaranteed deduplication of arbitrary idioms is claimed.
- **Word generation lifecycle — decided:** Rename the **persisted/internal** `Word.status` to `Word.generation_state` so it cannot be mistaken for sense-relation WSD status. Keep `pending` (no complete Word content published yet; may be a stub before generation or work in flight), `done` (a complete generated Word has been published), and `error` (generation/publish failed) as generation-state values; `pending` does **not** mean the LLM generated a complete Word that is merely waiting for relation resolution. Relation `pending` is separate and means WSD has not resolved the link. `generation_state` is a library lifecycle field, **not** a field the LLM emits in the generated Word output. Drop unused `not_found`: only selected existing Cambridge entries can be requested; an invalid ID or generation failure is an error, not a `not_found` Word or an `explanation` result.
- **Sense fields in the word-generation output:** `definitions[]` (nonempty), `pos`, **`tier`**, optional `cefr_level`, `examples[]`, `forms[]`, `patterns[]`, `collocations[]`, optional `register`, optional `usage_note`, optional `ipa_uk`/`ipa_us`, `relations[]`, `references[]`. **Drop** `domain`, `grammar`, `guideword`, and `connotation` from this target model. A sense's neutral definitions are equal-standing, meaning-preserving alternatives. Definitions and examples have **no persisted order, no first/canonical/default definition, and no position/order column**; choose and bind a specific definition when a downstream operation needs one. Do not force near-duplicate paraphrases merely to reach a fixed count. Preserve the **sense's** display order without equating it with `tier`: this is distinct from the deliberately unordered definitions/examples within a sense. Definitions/examples of another Style are separate rows scoped by `style_id`, not variants mapped one-to-one to the neutral rows.
- **Sense tier — four levels decided:** Retain `core` (foundational, very frequent), `common` (regularly encountered beyond foundational meanings), `extended` (less frequent or context-/domain-dependent), and `rare` (uncommon, archaic or highly specialized). Tier is an **estimated learning priority of each sense**, not question difficulty, CEFR, an exact frequency statistic or an obligatory distribution within a Word. A Word need not have exactly one `core` sense or any `core` sense. Remove the current system prompt's claim that `core` is always “the default meaning”; do not add a fifth level.
- **Selected-source synthesis — decided:** The selected Cambridge entry fixes the lexical item; pass its entry type, sense IDs, definitions and relevant examples/alternatives to the LLM. Look up WordNet using a reliable Cambridge-derived citation where available; do not blindly pass a display containing slot/alternative notation, and treat missing WordNet coverage as normal. Cambridge is primary, WordNet is optional supporting evidence that can contain noise. The LLM synthesizes learner-facing senses rather than copying source rows one-to-one: merge overlapping source senses, split genuinely distinct meanings when appropriate, ignore unrelated evidence, and add a well-established meaning missing from the supplied evidence when justified. This splits/merges **senses**, never emits additional Words from one request. Keep `references[]` per sense (zero, one or multiple Cambridge sense IDs/WordNet synset keys); code validates emitted citations against the evidence actually provided. Word-level association with the **selected Cambridge entry ID** is stored by code, not generated by the LLM. Update both generation prompts: remove the old instruction to emit multiple `units` for a bundled page, the rule that different fixed particles are automatically one alias, and the old `core` default-meaning wording. Provider or validation failures do not produce an `explanation` output.
- **Examples and inflection labels — updated decision:** Generate neutral `examples[]` **together with their Word/Senses**; generate each Style's examples together with its styled definitions the first time that Word–Style content is requested. **Remove `add_examples(sense_id, n, style/theme)` completely**, for neutral and styled senses, including `EnrichmentService.add_examples`, its separate provider/prompt/schema path, `ThemeService.append_examples`, associated repository append methods, tests, examples and public documentation. Additional on-demand Example generation is not needed; do not preserve it as a hidden enrichment hook or resurrect it simply because Word/Style content was generated once. Examples are learner content, not a rule-based question template. The `inf` in example target markup `<t inf="...">` and `forms[].inf` must be validated against **one shared inflection enum**, rather than relying on prompt instructions for markup. This does not reinstate the removed `grammar` field.
- **Alias/form/pattern boundary — decided:** `aliases[]` are Word-level **fixed alternative citations/spellings**, `forms[]` are **sense-level inflections**, and `patterns[]` are **sense-level licensed usage structures** (slots, grammatical positions and separability). These are not additional Word identities. For `take off`, the aircraft sense can use `take off`, while the remove-something sense licenses `take {sth} off`; for `put up with`, the object follows `with`, not `put`. Match a full anchored expression against an explicitly licensed structure, combining verified forms only with compatible patterns; do not permit arbitrary object insertion, wildcard token deletion, reordering, missing particles, or free inflection of fixed idioms. Represent real optional elements and lexical alternatives with **explicit bounded patterns** instead of interpreting every `/` or `(...)` as a wildcard; preserve literal notation such as `20/20 vision`. Fixed variants that really name the same Word belong in aliases, not in a second Word; a sense-specific grammatical use belongs in patterns. A Word need not invent patterns where lemma/aliases/forms already suffice.
- **Placeholder vocabulary — nine tokens decided for v1:** Use exactly `{sb}` (person/noun phrase), `{sth}` (thing or event as a noun phrase), `{one's}` (variable possessive), `{oneself}` (reflexive pronoun), `{place}` (location), `{doing}` (gerund/-ing verb phrase), `{do}` (base-form verb phrase; write a required `to` as a separate fixed token, e.g. `to {do}`), `{num}` (variable number), and `{clause}` (clause). These are typed **slots**, not wildcards that may swallow arbitrary words; a pattern must explicitly license each slot's position and bound its match. This closed vocabulary applies consistently to canonical idiom lemmas where a slot is necessary, sense-level `patterns[]`, relation target lemmas, and their code-derived matching/indexing. The current implementation supports only the first four tokens and must be extended/validated; LLMs must not invent a tenth token. `{one}` is **not** a token. Expand `someone/something` into separate licensed `{sb}` and `{sth}` patterns rather than making a combined token; express real optional elements and fixed lexical alternatives with explicit bounded patterns. `20/20` stays literal in `20/20 vision`: use `{num}` only when the specific structure permits a number. A literal word `someone`/`something` is not automatically a slot. This is the v1 set, **not** a claim that every Cambridge citation can be safely generalized; unrepresentable structures must remain literal or be reported as unsupported, never silently deleted or matched by an unrestricted wildcard.
- **Topics, not tags:** Use **topic** consistently for the redesigned product model. Topics remain **word-level** even for polysemous words; membership means at least one sense relates to the topic, not necessarily every sense. Accept that this is a noisy source of candidate vocabulary, not proof that an option is wrong; do not add a second per-sense topic taxonomy. `topics[]` selects names from the supplied existing vocabulary; `new_topics[]` defines only genuinely new names with `name` and `title`. Do not ask the LLM to repeat a title when reusing an existing topic. Merge both into the word's topic memberships on persistence; normalization must not create duplicates. The current `Tag`/`GeneratedTopic` names and `tag` field are old implementation terms, not target vocabulary.
- **Word relations:** LLM-authored `related[]` permits `word_family` (derivational relatives that are separate words, not inflections already in `forms[]` or surface `aliases[]`) and `confused_with` (learner-confusable words, not synonyms). Retain `part_of_phrasal_family` only as a system-derived link from phrase-reference data, **not** a relation the LLM emits. Remove `variant_of` (alias overlap), `arrow_redirect` (source navigation), and `another_word` (no useful semantics). No additional word-level relation types are agreed.
- **Sense relations:** Keep exactly `synonym`, `antonym`, `hypernym`, `hyponym`, `meronym`, `holonym`. `hypernym`/`hyponym` express type-of in opposite directions; `meronym`/`holonym` express part-of in opposite directions. Represent the intended direction without requiring the LLM to emit both sides of one link. `see_also` is already rejected above; add no catch-all relation. Collocations, inflected forms, and aliases are not sense-to-sense relations.
- **Relation identity contract:** In the redesigned generation JSON, a word-level `related[]` target carries canonical target `lemma` plus `rel_type`; a sense-level `relations[]` target additionally requires its `gloss` describing the **target's intended meaning**, and inherits its source sense from the containing sense. Do not drop `gloss` just because the target Word was found by lemma: WSD still needs it to select the target sense later. Persistence links the source Word/sense and target **Word ID** rather than storing an unverified free-text target indefinitely. Current schema calls the target string `norm`; this is old implementation terminology, not a second kind of lemma.

**LLM instruction for phrasal-verb/idiom lemma generation — agreed direction (apply equally to the generated Word and every relation target):**

```text
Write lemma as the stable dictionary headword for ONE lexical item, not an
inflected form, example sentence, definition, synonym, or usage pattern.

For a phrasal verb, use the base verb plus every fixed particle/preposition.
Exclude the subject, object, tense, and argument slots; put licensed object
positions and separable word orders in that sense's patterns. Never drop or
substitute a fixed particle: "look up" and "look up to" are different lemmas.

For an idiom, phrase, or expression, use its conventional citation form.
Preserve fixed articles, negation, contractions, prepositions and meaningful
punctuation. Where omitting a variable constituent breaks or changes the
headword, use one allowed canonical placeholder token. Do not alternate
between a literal citation word and a token for the same slot.

Use the selected Cambridge entry to identify the lexical item, but convert its
display notation to these rules. Choose one canonical citation
for equivalent alternatives; put accepted fixed alternatives in aliases and
licensed usage structures in sense-level patterns. Never merge genuinely
different headwords merely because a reference page groups them together.
Do not include slash/parenthesis alternatives, "etc.", or an example usage
in lemma. Apply all of these rules also to relation target lemmas. Use only
the allowed placeholder vocabulary; do not invent tokens or silently delete
an unknown constituent to make the headword shorter.
```

Reference examples: `put up with someone/something` → lemma `put up with`, patterns `put up with {sb}` and `put up with {sth}`; `took it off` → lemma `take off`, not a separate Word or a lemma `take {sth} off`; `the apple of someone's eye` → lemma `the apple of {one's} eye`, not `the apple of eye`. This prompt steers output but cannot guarantee that separately selected Cambridge entries will always yield the same citation for one lexical item; validate canonical forms on write and keep lemma-based Word identity instead of fuzzy-merging.

### Style — full resource, namespace, generation and storage contract

**Terminology and purpose — decided:** Use **Style** for the optional voice in which a consumer sees dictionary content; the current code's `Theme`, `ThemedSense` and `theme=` are implementation history, not a second product resource or names to preserve for compatibility. Style is **not** a topic (what the Word is about), a Sense's linguistic `register` (how that lexical sense is actually used), or a visual UI theme. It is a separate **content namespace** over the *same* generated Word and Sense IDs. For example, Harry Potter and Pirate can each have their own definitions and examples for the same sense of `glisten` or `shotgun`; neither creates a different lexical item or rewrites neutral content. Selecting Style is optional; `style=None` means neutral. What changes is the learner-facing wording and, when useful, the setting of examples/questions, **not what the Word means**. The governing instruction must explicitly say: **“Style changes the wording and the context of examples, not the sense's meaning.”** The headword, sense inventory, POS, tier, CEFR, inflections, licensed patterns, collocations, register, relations, topics, references and other lexical facts remain shared. The Style view combines these shared facts with definitions/examples from exactly the selected namespace; it is not a mutation of the neutral Word and not a shallow replacement of one string on an otherwise neutral view.

**Style fields and creation — decided:** The only *style-bearing fields* are `voice` (whose narrative voice or speaking perspective is used) and `diction` (choice and manner of language). Style also needs management identity such as internal `id`, stable unique `key`, and display `name`; those are identifiers/labels, **not additional creative axes**. A consumer's natural-language concept or style prompt is an **input used once to create the Style**: the model derives `voice` and `diction`, and the stored Style holds these structured results, **not the raw `style_prompt`**. Do not carry forward the old LLM-expanded free-form `style_prompt` as instructions for every later generation. Do not add `description`, `tone`, `material`, `setting`, or `scenarios` as stored Style fields. Retain management CRUD (create/list/get/update/delete) for this user-managed resource; its unique key is its durable handle rather than an LLM-generated lexical property. Keep the currently useful idea that changing a display name does not silently change an existing key. `voice` and `diction` are descriptions of a style, **not authority to override the task's system instructions or change a sense**. Exact creation and content-generation prompts are deferred to implementation/tuning; no test prompt in the discussion is an approved final prompt.

**Rejected material experiment — explicitly not part of the contract:** We explored a third `material` axis divided into `actors`, `places`, `objects`, `events`, and `motifs`, initially proposing X items in each group (X=8 in the Harry Potter example), then sampling those items into Word generation. That design is **withdrawn**: the 40-item pool could anchor the model to props, repeat the same scenes, consume tokens and induce a detail merely to tick a box. Neither those five arrays nor X, their sampling rules, “scene palettes”, or any other material subsystem should enter the target Style schema/provider input. Examples from Pirate, Harry Potter and the prompt trials illustrate the intended distinction between voice/context and meaning; they do **not** authorize new structured material fields.

**Namespaces and read semantics — decided:** Neutral Definition, Example and Question rows have `style_id=NULL`; content for a selected Style has `style_id=<that Style's id>`. Never use a missing Style row as a reason to show neutral definitions/examples/questions under the requested Style. A Word requested with an existing Style for which its styled content has **not** been generated returns **`None`**—not a Word with empty styled lists, not a partially neutral view, and not an implicit LLM request. Word reads are provider-free. With `style=None`, use only neutral Definition and Example rows. A selected Style's full Word view uses only that Style's Definition and Example rows for each sense plus the shared Word/Sense facts. No per-sense neutral fallback. A Question lookup/list/retrieve in a selected namespace similarly searches only that namespace; absence is `None`/`[]`, not a neutral Question or a generation trigger. Resolve an unknown Style as an invalid requested resource rather than presenting neutral content under its name. Do not let absence of one styled sense masquerade as a fully styled Word: the styled Word is published as a complete per-Word set.

**Neutral-first Word generation and one-time Style generation — decided:** `generate(available_id, style=None)` retains the selected-source Word contract: return an already-done neutral Word unchanged, or generate and persist it once if missing, including its neutral examples. If a Style is specified, ensure the neutral Word exists first; then check that this Word already has a complete set of styled definitions/examples for that Style. If present, return the existing styled Word without generating new definitions/examples. If absent, generate **both** styled definitions and examples for that Word in the requested Style and return the resulting styled Word. This is **create-if-missing/reuse**, including when the consumer is handling a batch of Word generation requests; it is neither a `force` overwrite nor a request to append more definitions/examples every time. **There is no `add_examples` augmentation API or separate example-generation provider path** for either namespace. Do **not** call `generate_questions` during Word or Style generation. Provider failure or invalid styled output is an error, not a neutral fallback or a fabricated partial Style view. The consumer owns coordination of overlapping calls; no new cross-call single-flight, queue or retry architecture follows from the one-time semantics.

**Styled Definition/Example LLM input and cardinality — decided:** Style generation works at **Word scope**, over the list of that Word's senses. For each sense, select **exactly one** of its neutral definitions as a meaning anchor; do not pass all neutral definitions/examples just to force paraphrase-by-paraphrase correspondence. Give the model that list of senses with one meaning anchor each, plus the Style's `voice` and `diction`, the target Word needed to write actual example sentences, and the requested **K styled definitions and M styled examples per sense**. One output group maps to each input *sense*; K definitions and M examples in it are free-standing content for that sense, not matched one-to-one to neutral definitions/examples and not matched to one another. The list alignment within the **generation exchange** can associate returned groups with sense IDs in code; it does **not** create a persisted definition/example order. LLM output does not choose IDs or source provenance. Validate the intended number of sense groups and requested cardinalities before publishing the Word's styled content; store a complete result for all the Word's senses as one per-call atomic write so a half-styled Word is not treated as available. There is no need for a `styled_senses` marker/status row, generation job state, or K/M tracking column just to mark existence: styled rows and the per-call write contract serve the intended view. This is an explicit generate-if-missing operation, **unlike** recurring Question generation below.

**Definition/Example behavior and deferred prompt tuning — decided boundary, not a frozen prompt:** Styled definitions may express a sense in a noticeably different narrative voice and use a brief fitting illustration; they must still explain the same Word/sense outside the fictional setting. They may not turn a scoped image into a universal restriction or add a new essential property, usage condition, ingredient, ability or function. In particular, a Harry Potter definition of `shotgun` must still describe a firearm; it must not become a magical weapon or exclude the stored neutral sense's ability to fire a slug simply to emphasize pellets. An illustrative Harry Potter definition of the magical sense of `potion` may evoke a cauldron **as an example**, not assert that all potions are heated in cauldrons, drunk, medicinal, or made of specified magical ingredients. A definition that merely repeats the neutral sentence with synonyms is accurate but does not deliver much Style value. If styling would obscure the meaning, prefer a clear, less-styled definition. Do not force near-duplicate definitions just to pretend a simple sense has K genuinely different explanations; the trial with K=3 exposed this risk, and the exact way to tune K/prompts is **deferred**, not silently changed here.

Examples must be **natural use of the target in that specific sense**, with valid `<t inf="...">...</t>` tags and a context that teaches or helps recall its meaning or grammatical usage. A sentence that merely places the Word beside a professor, library, castle, pirate ship or other Style prop has not become a useful example; a character reciting the definition is likewise not a usage example. Where appropriate, show the Word acting or being used and vary situations/constructions across M examples. A themed `glisten` example can use raindrops catching light on a castle window; the reflected-light meaning must remain recognizable. For `shotgun`, a natural, informative clay-target context is better than three fan-fiction scenes in which somebody finds or stores an unexplained gun. `potion` naturally accommodates school/cauldron imagery, yet a lesson, recipe and magical effect should not collapse into several near-duplicate examples. Do not require all M examples to advertise the Style or insert material when it hurts the teaching purpose. Definition clarity and useful examples take precedence over intensity of theme. The detailed generation prompt wording, balance of recognizability versus accuracy, and empirical tuning are **deferred**; do not turn this discussion's experimental prompts, sample outputs, or critique into a quality-control/automatic-regeneration subsystem.

**What the prompt trials actually taught (not new mandatory prompt fields):** Early `shotgun` output repeated nearly identical neutral definitions and put a professor, Ministry official and library around the noun without showing its meaning. Later prompts made Harry Potter more recognizable but claimed a shotgun fires pellets *instead of* one single projectile, although the input definition also permitted a slug; examples included an exposition of what the gun is and an entertaining giant bending its barrel, neither a substitute for teaching ordinary usage. `potion` results improved the setting of examples, but successive definitions narrowed the word to a drink, a cauldron, herbs/roots, or a recipe-derived magical power not licensed by the neutral input. A sleeping potion showing its effect helped; a sentence calling a bottled potion a “love charm” conflated different lexical things. These are observations for later prompt work, **not** evidence that Style may change facts or that material fields should be restored. The user explicitly deferred instruction tuning after seeing this trade-off.

**Question generation is fundamentally different — decided correction:** A neutral/Style Word's Definition+Example set is generated **once and reused**. By contrast, each explicit `generate_questions(sense_id, question_type, count, *, distractor_count, style=None)` call **adds `count` new Question artifacts**, even when the sense/Style already has questions. Use one LLM request per call for those N same-type questions, each with K distractors as required; no fixed question pool ceiling, no “already exists, return the old questions” shortcut, and no auto-generation merely because someone read a Word. Questions are separate persisted artifacts bound to a sense and one namespace. Their own displayed content/options can reflect that Style's voice/diction and styled Definition/Example evidence, while the target Word and sense, answer correctness and grading rules stay the same. A requested Style needs existing styled content; a Question read never creates it. `get_question(id)` and `grade_answer(id, ...)` already know the artifact's namespace and do not need a Style argument. `list_questions`/`retrieve_question` filter by sense and optional type **and Style**; `style=None` means neutral, not “all namespaces”. A Question's answer/explanations are stored with that artifact, not recomputed from whatever Definition/Example happens to be displayed later. This extends, not replaces, the seven full per-type contracts below.

**Update/delete lifecycle — decided simplicity:** Changing `voice` or `diction` leaves all previously generated styled definitions, examples and questions **as they are**. Do not delete them, rewrite their text, introduce version/epoch/invalidation machinery, or silently regenerate them when Style metadata is updated; new Question requests may use the then-current Style while old artifacts remain saved. Delete a Style → delete its namespaced Definition/Example/Question rows, **not** the neutral rows and not the underlying Word/Sense. Delete a Sense/Word → delete its neutral and styled children by FK cascade. `style_id` on a row deleted with its Style must never be set to `NULL` (which would mislabel styled content as neutral). The Style CRUD itself remains available because the consumer owns the resource, unlike Question, whose generated artifacts can be deleted but have no `update_question` requirement.

**Target logical relational schema — decided (only the Style-affected portion shown; other Word/Sense children remain shared):**

```text
styles
  id              primary key
  key             unique stable identifier
  name            display label
  voice           style-bearing field
  diction         style-bearing field
  # no persisted style_prompt, description, tone, material, setting, scenarios

words
  id              primary key
  ...             neutral/shared Word identity and data

senses
  id              primary key
  word_id         non-null FK -> words.id ON DELETE CASCADE
  ...             shared POS/tier/forms/patterns/relations/etc., NOT a single definition column

definitions
  id              primary key
  sense_id        non-null FK -> senses.id ON DELETE CASCADE
  style_id        nullable FK -> styles.id ON DELETE CASCADE
  content         non-null text
  # many rows per (sense_id, style_id); NULL = neutral; no order/position

examples
  id              primary key
  sense_id        non-null FK -> senses.id ON DELETE CASCADE
  style_id        nullable FK -> styles.id ON DELETE CASCADE
  content         non-null text, with validated target markup where applicable
  # many rows per (sense_id, style_id); NULL = neutral; no order/position

questions
  id              primary key
  sense_id        non-null FK -> senses.id ON DELETE CASCADE
  style_id        nullable FK -> styles.id ON DELETE CASCADE
  question_type   one of the seven decided types
  ...             saved type-specific artifact: content, correct-answer material,
                  distractor bank and per-choice explanations where applicable
  # many rows per (sense_id, style_id, question_type); NULL = neutral
```

The nullable `style_id` is the **only neutral-versus-Style discriminator** on these content rows. Do not add `styled_senses`, `styled_definitions` or `styled_examples`; do not retain the old `senses.definition` and `themed_senses.definition` as the target storage for lists of definitions. Use **`content`**, not `text`, as the field/column name for Definition and Example. There is deliberately no `definition_order`, `example_order`, `position`, canonical/default flag, or `UNIQUE(sense_id, style_id)` on any of the three content tables: the latter would disallow multiple Definition/Example/Question rows. Sense ordering for displaying a Word is a separate, preserved property of `senses`, and distractor ordering by confusability inside a Question artifact is separate too. Store question options/payload in a representation that preserves its already-agreed grading and answer-safety contract; choosing JSON versus more child tables and an opaque choice-ID encoding is implementation detail, not permission to change the namespace or question semantics. Index/lookup choices should support filtering content by sense and requested `style_id` without changing the logical model. The schema of Cambridge's read-only database is unaffected.

**Cross-module follow-through:** Current code assumes `Sense.definition`, `Example.text`, `ThemedSense`, `ThemedExample`, a single chosen definition, optional neutral fallback and theme-specific locks; none of those storage/read assumptions is the target model. Word generation, Word read views, Question builders/grading and WSD inputs/content hashes must select an appropriate definition **explicitly** when they need one; translation should accept an explicitly selected text fragment, not assume a Sense has one definition. TTS is removed entirely. They must not treat incidental DB row order as a default definition, leak source provenance into the public surface, or make a derived Question depend on the survival/order of a Definition row rather than its saved artifact. This section records a design to implement later, not completed code.

### Translation cache and TTS removal

**No persisted model provenance — latest decision:** Do **not** add `model_id` to Word, Sense, Style, Definition, Example, Question, translation cache or any other AI-generated data; it is not needed at present. Do not make the translation cache vary by model. Do not add `prompt_version` or a prompt-versioning subsystem either. These deliberately omitted fields are not an invitation to reintroduce provenance indirectly as a required cache key or extra table.

**Translation remains; TTS does not — decided:** Translation is an LLM operation, with a DB-cached translated string on a cache hit and a provider call on a miss. Remove TTS **entirely for this release**; a future TTS implementation may be designed later, but no stub, public `tts_sense`/`tts_field`/`tts_many` API, audio provider, model/voice/format configuration, TTS vocab, binary Asset/file-store subsystem, `file_path`, staged/fsynced file writes, file-replacement/unlink-after-commit listeners, local file-write locks, orphan file sweeper, audio tests/examples/docs or `audio.speech.create()` path should survive just to anticipate it. This is not merely removal of the `tts_many` convenience wrapper. Keep any translation-specific security behavior that is still real (e.g. treating input text as untrusted data, explicit missing-provider errors, bounded requests); do not preserve audio safety machinery on its behalf.

**Why the current Asset lookup no longer fits:** Current `lexi_ai/assets.py` / `lexi_ai/db/queries/asset.py` resolves `source_kind + source_id` from only `sense_def`, `example`, or `collocation`; `assets` has UNIQUE `(source_kind, source_id, kind, params)` and a *separate* `content_hash` of normalized source text to check for stale rows. In the current implementation **the hash is NOT the database cache key**, and `file_path` is only a TTS output path, not a translation key. `get_asset(id)` reads an Asset row without the source-text hash verification that `translate_field` uses. The current `translate_sense(sense_id)`/`tts_sense(sense_id)` presumes one `Sense.definition`, which the new unordered `definitions` table explicitly rejects. More importantly, a Question distractor's explanation can be nested in its saved payload rather than have a standalone source-table row; a `source_kind`/row-ID whitelist cannot address such a fragment without field-path identifiers and polymorphic source-specific plumbing. The consumer needs to translate a **selected string of content** such as `definition.content`, `example.content`, or `distractor.explanation`, not require a fabricated row or a Sense ID. `file_path` is not an alternative cache key for this use case.

**Translation API and hash-key identity — decided:** Translate the actual input text into a target language (conceptually `translate_text(content, target_language) -> translated_string`) rather than extending `translate_field(source_kind, source_id, ...)`, per-source resolvers, `source_hash`, definition-specific convenience methods, or field paths for every nested explanation. The cache key is **(hash of the exact text sent to the translator, target language)**. A changed text yields a different key naturally; identical input text in a Definition, Example or Question explanation can reuse one translation. **No model ID or prompt version participates**, and neither is persisted. Do not hash one normalized string while sending another string to the provider: cache identity must correspond to the provider's actual text input. Unlike the old reference-key + read-time source-hash design, this text-addressed cache needs no FK-like GC of translations when a Word, Style, Definition or Question is deleted. Keep a DB uniqueness constraint on the cache key and simple cache inspection/deletion/purge for consumers; there is no file or file-orphan lifecycle after TTS removal. Do not add source-row tracking, per-field paths, cross-call locks, or a model-version cache layer just to support hypothetical future behavior.

**Minimal logical cache table:** A translation cache row needs a local `id` for existing management use cases, `input_hash`, `target_language`, and translated `content`, with `UNIQUE(input_hash, target_language)`. It is **not** a child of a Word, Sense, Definition, Example, Question, Style, or Cambridge row; identical input text across those locations intentionally converges on the same cache entry. No `source_kind`, `source_id`, `kind` switch, `params` blob, `content_hash` as an extra verification field, binary `file_path`, `voice`, `format`, `model_id`, or `prompt_version` is required for this translation-only cache. Provider calls and cache writes are explicit on misses. Management may list/get/delete/purge cached translations without exposing or recreating the old polymorphic Asset abstraction.

**Overengineering audit of today's implementation:** The old `AssetRepository` mixes in-memory local file locking, SQLAlchemy transaction-end event listeners, on-disk write staging and collision avoidance, filesystem GC, a cross-table source resolver, source-hash verification, translation, audio and batch wrappers. Most of that exists for file-backed TTS and reference-keyed sources, **not** for a translation that returns a DB text value. In the translation-only target, remove dead audio/file code and avoid recreating it under a new name. Preserve only the useful translation behavior: valid target language/input, a simple cache identity, a safe cache hit/miss + atomic DB write, explicit provider failure, and consumer-usable cache management. Naming the surviving class `AssetService` or `TranslationService` is secondary to actually removing unnecessary responsibilities; the `Service` suffix alone is not an overengineering finding.

### Question design — full generation, presentation and grading contract

**Keep this section detailed as decisions evolve:** For each question type, record what the generator receives, what it produces or reuses, what each format displays, and how it is graded. A one-line type/format inventory is not a substitute for the per-type contract below. These are product decisions for future implementation, **not a description of the current question plugins or prompts**.

**Shared boundaries:** There are seven question types and three response formats: `single_choice`, `single_word`, `short_answer`. The first three `*_to_word` types support `single_choice` + `single_word`; `word_to_definition` and `word_to_usage` support `single_choice` + `short_answer`; `dialogue_completion` and `meaning_in_context` support only `single_choice` (12 type/format pairs). A **type** determines what the learner must understand; a **format** determines how they respond. `single_word` means one vocabulary item, including a multiword expression, not one whitespace-delimited token. `short_answer` is designed only for the two `word_to_*` types below and has different grading in each; do not generalize it to the others. All learner-facing content and feedback are in English. Neither type nor format determines question difficulty; no difficulty policy is decided.

**Free-text grading output:** `single_word` and both designed `short_answer` tasks return exactly the fields `result` and `sense_id: int | null`, not a mandated model/class name. The allowable `result` values depend on the task: `correct`/`incorrect`/`typo` for `single_word` and `word_to_usage / short_answer`; only `correct`/`incorrect` for `word_to_definition / short_answer`. A wrong or typo answer always returns `sense_id=null`; a correct answer has the sense ID described under its task (or null when a correct `single_word` alternative has no stored sense). No separate text explanation is returned by a free-text grader.

**Batch-generate new questions on every call, then reuse each saved artifact:** The consumer chooses when to request questions for a target Word/sense; generating a Word or its styled Definition/Example rows does not generate questions. **Every explicit call** makes **one LLM request for N NEW questions of one selected type for one sense**, even if that sense/Style already has questions; question count grows by adding artifacts, unlike once-per-Style Definition/Example creation. For `style=None`, use neutral content; for a specified Style, use that namespace's styled content and the shared Word/Sense facts, never an implicit neutral fallback. Give the generator relevant definition/example/forms/usage evidence and requested distractor count **K** as needed by the type. Persist N separate question artifacts, each reusable across all formats its type supports; never generate one artifact per format or call the LLM again on presentation. Each artifact carries its target sense, its nullable `style_id`, question content or bound source definition/word, saved correct-answer material and K generated distractors where applicable. Where the correct answer comes from stored `definitions[]`, bind the relevant sense and its appropriate **same-namespace** definition alternatives rather than inventing a new definition. For every type with `single_choice`, provide a correct option plus K distractors, with a short English explanation for the correct option and each wrong option. Order generated distractors from most to least confusable with the correct option; **the trusted consumer** selects three from the saved bank, shuffles them with the correct option, and reveals explanations only after the answer. The distractor order is part of the Question bank, **not** a persisted order for Definition or Example rows. K is the requested bank size **per generated question**, not an extra generation call per display. Choice grading uses the saved correct option; no Jev call. Do not add rule-generated filler, a quality-scoring subsystem or automatic regeneration merely because an LLM answer might be imperfect; improve generation instructions.

**Content and marking:** `content` contains only the question's sentence, situation, paragraph or structured dialogue, **never** an instruction such as “Choose the correct word” or “Fill in the blank”; the UI supplies the task wording. `context_to_word` and `cloze_to_word` have the same generated fields (`content`, `correct_answer`, `distractors`, each answer with its explanation); only the content-generation instructions differ. For any question that shows the target Word directly **in question content, not merely in an answer**, mark its actual surface with `<t inf="...">...</t>`; `inf` is the form actually used (`base`, `past`, `past_participle`, `present_3sg`, `ing`, `plural`, `comparative`, `superlative`). Follow the existing example contract in `lexi_ai/prompts/_partials/target_markup.jinja`: mark each part of a multiword target separately when needed, including separable constructions. This is for UI highlighting, not literal user-visible XML. The same rule applies if the displayed question consists of the target word itself (e.g. `word_to_definition`/`word_to_usage`), and to target occurrences inside structured dialogue; do not mark a target that appears **only** in answer options. Do not confuse these tags with the one literal `_` that denotes a `cloze_to_word` blank.

#### `definition_to_word` — `single_choice` and `single_word`

- **Input and generated artifact:** Start with the target Word/sense and **choose one of its definitions in the Question's selected namespace**; there is no first/default definition or stored definition order. Bind the selected definition's content to this Question artifact. Present that content without the target word. Give the LLM the Word and exactly this definition to generate K **word/expression** distractors, sorted by confusability, with a brief explanation of why the saved correct word fits and why each distractor does not. Bind this bank to that definition; other equal-standing definitions of the same sense are not swapped into the same artifact, because a distractor might fit another wording. Do not mechanically derive distractors from topics/relations or silently replace the LLM's bank with rule-generated alternatives. A styled Question uses a styled definition; it does not silently show a neutral definition in a Style view.
- **Presentation/grade:** `single_choice` displays the definition plus the saved correct word and three sampled distractors, grades by the saved option, and reveals explanations afterwards. `single_word` displays the **same definition without options**, accepts a learner's one vocabulary item (including a multiword expression), and uses the shared `single_word` grading contract below. Keep the exact saved correct-answer surface and its sense ID for the fast path; do not equate an inflected saved answer with the Word's citation lemma by accident.

#### `context_to_word` — `single_choice` and `single_word`

- **Input and generated artifact:** Give the LLM the target Word and intended sense, with the selected namespace's content when a Style is requested. It creates a brief, plausible **situation** as `content` (Style may affect its context without changing the intended meaning), plus the fitting `correct_answer`, K word/expression distractors and their respective explanations. For neutral content, this can be an ordinary real-life situation. The target word is **not named in the content**. The learner supplies a word appropriate for the situation; this is not a sentence with a blank or a blank cut mechanically out of a stored dictionary example. The LLM must emit only the situation as `content`, not an extra instruction asking which word fits. Save the answer as it is actually meant to be submitted, including the relevant inflection or multiword surface.
- **Presentation/grade:** `single_choice` samples three saved distractors and grades by known option. `single_word` shows the same situation with no options and uses the shared `single_word` Jev flow; a different correct expression can be accepted even if absent from the generated options.

#### `cloze_to_word` — `single_choice` and `single_word`

- **Input and generated artifact:** Supply the same target Word/sense and K as for `context_to_word`, but instruct the LLM to write `content` as **one sentence or short passage with exactly one literal `_`** replacing the entire required answer, even if the answer is a multiword expression. Generate the **exact form that fills that blank** as `correct_answer` (it may differ from the lemma), K word/expression distractors and their explanations. The context should make the intended sense and grammar clear; it is not an extra “fill this in” instruction. The rest of the generation/output contract is the same as `context_to_word`; only this content instruction differs. Example: `As the plane accelerated down the runway, it _.` → `took off` (one underscore, not one per word).
- **Presentation/grade:** `single_choice` presents the same blank with the saved correct surface and three distractors; `single_word` presents the blank with no options and grades through the same shared `single_word` flow. A normalized exact match must compare against `took off` in this example, **not** automatically against `take off`.

#### `word_to_definition` — `single_choice` and `short_answer`

- **Input and generated artifact:** The question shows the target Word (marked with `<t inf="...">` when embedded in the displayed content); its generated sense has equal-standing `definitions[]` **in the selected neutral or Style namespace**, with no first/default member. Give the LLM the target Word/sense and its same-namespace definitions to generate **K definition distractors**, sorted from hardest to easiest to distinguish, and explanations contrasting each distractor with the intended meaning. Save/bind the correct-definition alternatives and their explanation material with the Question artifact so a presentation may choose **one** of those alternatives at random as the correct choice; do not treat incidental table row order or a subsequently deleted/replaced definition as the answer key. The distractor bank belongs to the intended sense and must not assume that only one phrasing is a valid definition. No separate LLM question or distractor call is needed for `short_answer`.
- **Presentation/grade:** `single_choice` shows the Word and the selected correct definition plus three distractors, using the saved correct option for grading and showing explanations only after the choice. `short_answer` shows the **same Word without options** and asks the learner to explain it in their own words; no per-answer explanation or typo classification. It does **not** secretly require the originally selected target sense if the word has other stored senses: Jev selects which of this Word's senses, if any, the learner actually defined, as specified below.

#### `word_to_usage` — `single_choice` and `short_answer`

- **Input and generated artifact:** Show the target Word **and the particular meaning being tested**, so multiple senses are not conflated; mark the target surface in the question with `<t inf="...">`. Give the LLM the Word, target sense and relevant usage evidence to generate one natural sentence **using that Word in that sense**, K candidate sentences using the Word incorrectly or in another sense, and English explanations for all choices. The options are **sentences**, not definition text. The Word/meaning shown in the question is the shared artifact for both formats; the LLM does not generate a new prompt for each format.
- **Presentation/grade:** `single_choice` asks which option uses the Word with the displayed meaning, samples three distractor sentences, and grades by the saved correct option. `short_answer` shows the same Word and meaning **without choices**; the learner writes their own sentence using the required Word. Correct use of an appropriate form, grammar and intended sense → `correct`, target sense ID; correcting **only spelling** to make the sentence a correct use → `typo`, null; wrong sense, wrong construction, or a synonym **instead of the required Word** → `incorrect`, null. For the aircraft sense of `take off`: `The plane took off at dawn.` → correct; `The plane took of at dawn.` → typo; `She took off her coat.` or `The plane lifted off at dawn.` → incorrect. This is Jev-judged free text, **not** Choice sense-mapping across the dictionary; the target sense is already known. No answer-specific explanation is returned.

#### `dialogue_completion` — `single_choice` only

- **Input and generated artifact:** Give the LLM the target Word/sense and K. Generate `content` as a **structured list of dialogue turns**, not one string containing `A:`/`B:` lines: `[{"speaker": "Maya", "text": "I'm <t inf=\"base\">reluctant</t> to accept the job."}, {"speaker": "Leo", "text": null}]`. Every `speaker` is a **one-word human name** such as Maya or Leo, never A/B/C. The target Word appears visibly and tagged in a spoken turn; `text: null` is the missing reply, not a literal `_` in the dialogue. Generate one natural reply that follows from the conversation, K less suitable replies ranked by confusability, and an explanation for each. The question type is about **completing a dialogue**, not called `word_to_dialogue` merely because the target Word appears.
- **Presentation/grade:** UI renders the speakers/turns and asks the learner to choose the missing reply; it does not print raw markup or generate a textual instruction inside the dialogue. Present the correct reply with three sampled distractors and grade by known option. Example correct reply to Maya above: `What is making you hesitate?` A response such as `Congratulations on accepting it!` wrongly assumes she decided already. No `single_word` or `short_answer` variant is designed.

#### `meaning_in_context` — `single_choice` only

- **Input and generated artifact:** Give the LLM the target Word/sense and K. Generate `content` as a short passage or sentence that **uses the tagged target Word** and makes the intended sense inferable from surrounding language. Also generate a correct option that **interprets what the Word means in this specific passage**, K plausible but incorrect interpretations ranked by confusability, and explanations for all options. Do **not** simply paste a stored sense definition into the correct choice; rephrase it for the actual situation. Example content: `The café didn't <t inf="base">charge</t> us for the extra bread.` Correct interpretation: `The extra bread was free.` A distractor such as `They added the bread to our bill to be paid later.` is a different interpretation. AI generates **both** correct and wrong choices, not just the passage.
- **Presentation/grade:** Show the generated content and one correct interpretation plus three sampled distractors; UI asks what the highlighted word means **here**, and grades by saved option. This tests contextual sense interpretation, distinct from defining an isolated Word or choosing a word to fit a situation. No `single_word` or `short_answer` variant is designed.

#### `single_word` grading shared by the three `*_to_word` types

- **`single_word` output and shortcut — decided:** The result has **exactly two fields**, `result: "correct" | "incorrect" | "typo"` and `sense_id: int | null`. These are fields, **not a mandated model/class name**; `sense_id` uses the library's existing integer sense IDs, not UUID. Normalize harmless differences (Unicode representation, case and redundant whitespace) consistently; never autocorrect or erase meaningful particles, objects, punctuation, hyphens or apostrophes. The exact peripheral-punctuation policy remains to be specified. A normalized exact match to the **saved correct-answer surface** (which may be an inflected form rather than the target lemma) still returns `result="correct"` and its bound sense ID without Jev; do not treat every multiple-choice option as correct. Other answers use the single-request decision below. A correctly spelled form, alias, variant or different expression can be correct when it fits the exercise; a spelling-only error that would otherwise be correct is `typo`, not `incorrect`.
- **Consumer-owned mastery for free-text grades — decided:** The consumer already knows the exercise's `target_sense_id`; grading does not echo it when the learner is wrong. For `correct` with `sense_id` equal to the target, increment target mastery; for `correct` with a different resolved `sense_id` (an alternative expression or another valid definition of the displayed Word), increment **that sense's** mastery. For `correct` with `sense_id=null`, change no sense mastery. For `typo`, change no sense mastery, whether the intended answer was target or external. For `incorrect`, decrement **target** mastery and return `sense_id=null`, regardless of which different word or meaning the learner wrote. `typo` applies **only if correcting spelling alone would make the submitted answer fit the exercise**; a misspelled expression that still has the wrong meaning is `incorrect`.
- **One Jev request — decided:** Before calling Jev, retrieve a bounded set of plausible **generated Lexi-AI Word senses** from `user_answer`, allowing fuzzy suggestions after stronger lemma/alias/form/pattern matches. Fuzzy retrieval supplies candidates; it never awards correctness. Submit one state containing `exercise_context` (the definition or situation) and `user_answer` as written, **not a target Word/answer ID**, with three independent questions in the **same API request**: `meaning_fit` (Noul), `spelling_valid` (Noul) and `matched_sense` (Choice). Choice criteria list candidate senses from potentially **multiple Words** as `word — POS — definition`, plus `no_candidate`; use opaque option keys and map the chosen key to the stored integer sense ID in code. The Choice is evaluated eagerly, even when the final result is typo/incorrect, but its result is **used only when both Nouls are true**. No sequential second Jev request and no incorrect/typo sense resolution. The existing shared Jev/LLM adapter owns any applicable fallback; do not create bespoke per-question fallback prompts.

**Jev question instructions — agreed direction (English; keep the two Noul judgments independent):**

```text
meaning_fit (Noul): Ignoring only clear spelling errors in user_answer,
would the intended expression appropriately answer exercise_context?
Preserve the actual lexical expression, its objects, particles, word order
and grammatical construction. Do not turn a different valid expression into
the answer by replacing words, dropping an object or changing its meaning.
An obvious spelling-only repair can count; a repair that still gives the
wrong meaning cannot.

spelling_valid (Noul): Is user_answer correctly written as the English
expression it submits in this context, exactly as written? Do not
autocorrect. Check the expression as a whole, not just whether each token
is an English word: "take of"/"lift of" are misspelled here although "of"
is a word; "take out" is spelled correctly even if it is the wrong answer.
Do not decide whether its meaning fits in this question.

matched_sense (Choice): Which listed vocabulary sense, if any, is expressed
by user_answer in exercise_context? Use the submitted expression's words,
objects and grammatical construction. Choose no_candidate if none of the
listed senses represents the answer; do not choose a sense merely because
its definition matches the exercise while its word differs from the answer.
```

For `meaning_fit`, the true criterion is “the submitted expression answers the exercise as written or after an obvious spelling-only repair”; false is “it still has the wrong meaning or construction after any spelling-only repair.” For `spelling_valid`, true is “the submitted expression is correctly spelled as a whole, regardless of semantic fit”; false is “its intended expression is misspelled as submitted, even if individual tokens are real words.” These are two separate Noul questions over the same state, not a request for Jev to output a corrected string.

**Decision from the two Nouls:** Each Noul yes-probability `>= 0.7` is true and `< 0.7` is false. `meaning_fit=true, spelling_valid=true` → `correct`; use the Choice-mapped sense ID if usable, otherwise `null`. `meaning_fit=true, spelling_valid=false` → `typo`, `sense_id=null`. `meaning_fit=false` → `incorrect`, `sense_id=null` regardless of spelling. The global `0.7` Jev policy for applicable Choice confidence/fallback remains in force; the two Noul probabilities and Choice confidence are distinct measures. `no_candidate`, absent Lexi-AI sense, or no usable Choice resolution **does not change `correct` into `incorrect`**.

**Expected behavior to verify, not observed Jev output:** For an aircraft leaving the ground, `take off` → `correct` with its aircraft sense; `lift off` → `correct` with its own sense; `take of` and `lift of` → `typo`, `null`; `take it off`, `take it of` and `take out` → `incorrect`, `null`. A valid alternative absent from Lexi-AI may be `correct`, `null`. Test real-word substitutions and misspellings of wrong-meaning expressions so `meaning_fit` does not silently repair semantics; check the model's actual responses rather than assuming the instructions guarantee these outcomes.

#### `word_to_definition / short_answer` — Jev sense-selection contract

Submit **one Choice** question. Its `state` contains the displayed **Word** and the learner's `user_answer`; it does **not** contain the exercise's hidden target sense, a reference source or a correct-definition answer key. List **all stored senses of that Word** as criteria, each described by Word, POS and relevant definition(s) of the meaning, plus `no_sense`. The **style namespace of the displayed Question does not alter which Word/Senses exist or what counts as an accurate definition**: an accurate neutral paraphrase of a styled sense must still be accepted, and Style-specific wording is not required of the learner. Do not let a colorful styled phrasing redefine a sense for grading. Use neutral criterion `The answer does not accurately define any listed sense.` for `no_sense`: do not inject the Word into that criterion. Map opaque option keys to internal **integer sense IDs** in code, never request an ID from Jev. This is definition evaluation, **not semantic retrieval**: mentioning something related to a Word does not define that Word. A learner paraphrase can be correct even if it does not repeat the saved wording. The agreed short instruction is:

```text
Which sense of `word` does `user_answer` actually define? Accept accurate paraphrases, but do not choose a sense merely because the answer is related to it. If the answer defines a different thing, choose `no_sense`.
```

Choosing any stored sense → `result="correct"`, `sense_id` = that sense; choosing `no_sense` → `result="incorrect"`, `sense_id=null`. There is **no `typo` outcome**, answer-specific explanation, additional Noul, or second Choice. For `bank`, `A place that keeps your money safe` should map to the financial-institution sense despite not matching its wording; `A machine that lets you withdraw cash using a card` defines an ATM, not a bank, and should map to `no_sense`. These are expectations for instruction testing, not guarantees from the model or a request for a special-case rule. The agreed global Jev Choice confidence/fallback threshold is 0.7.

#### `word_to_usage / short_answer` — Jev judgment boundary

The submitted answer is **a whole sentence written by the learner**, not a definition or a vocabulary-item string. Judge whether it actually uses the **required displayed Word** (including a legitimate inflected/structural form) with the displayed target sense in a grammatical sentence; evaluate spelling separately from fit so an otherwise valid use with only a spelling error can be `typo`. A misspelling of a wrong-sense use stays `incorrect`. Do not search for an unrelated Word/sense and award it as a correct external answer: unlike `single_word`, the task explicitly requires this Word and sense. Its response has the same two **fields** `result` and `sense_id` as the other text grades, with `correct` → target sense ID and `typo`/`incorrect` → null. The consumer-owned mastery rules above apply. No Choice to identify an external sense, no answer-specific explanation, and no separate LLM question generation for this format. The precise Jev question wording for this free-sentence judgment will be written during implementation; do not present the `single_word` 2-Noul/1-Choice prompt as if it were already agreed for this different task.

### Question module — replacement architecture and public resource contract

**This replaces the current question engine rather than wrapping it.** The seven types, 12 allowed type/format pairs and grading rules above are the closed product design. Treat Question as a persisted **child of Sense in a neutral-or-Style namespace**, much like other named resources on `Lexicon`: generation **appends new questions every time it is called**; get/list/retrieve are pure reads; deletion is explicit. The consumer owns when to request generation and when to show a stored question. Questions are **not** generated along with Words/styled Word content, on reads, or per presentation format. This intentionally differs from neutral/Style Definition+Example generation, which reuses an existing set instead of appending on `generate`.

**Public API (operation names, not mandated class/model names):**

```text
generate_questions(sense_id, question_type, count, *, distractor_count, style=None) -> list[Question]
get_question(question_id) -> Question | None
list_questions(sense_id, question_type=None, *, style=None) -> list[Question]
retrieve_question(sense_id, question_type=None, *, style=None) -> Question | None
delete_question(question_id) -> bool
grade_answer(question_id, format, answer) -> {result, sense_id}
```

- **Create:** **Every** explicit `generate_questions` call makes **one LLM request** to generate `count` **additional** questions for **one sense and one type**, each with `distractor_count` (K) distractors and the per-type correct answer/explanations. Existing Question rows are **not** a cache hit for generation: persist each newly generated Question with its own ID and nullable `style_id`, usable in every allowed format without another generation request. `style=None` selects neutral; a Style selects its existing styled content for generation without remaking it. `count` is the number of **new questions**, K the number of distractors **per new question**; neither is a difficulty level, total pool cap, or number of presentation formats. No per-question LLM fan-out, internal batch worker, implicit generation or plugin-wide “prepare all applicable types.” A provider/generation failure is an error, **not** an empty retrieval result. The consumer coordinates overlapping calls; the library keeps per-call write integrity without introducing cross-call locks/queues.
- **Get/list/retrieve:** `get_question(id)` gets **that exact stored artifact** (and its namespace) or `None`. `list_questions(sense_id, question_type=None, style=None)` lists stored questions only in the specified neutral/Style namespace, optionally one type, or `[]`. `retrieve_question(sense_id, question_type=None, style=None)` selects **one existing question** from that same namespace (random among matches), optionally limited to one type, or `None`. `style=None` means neutral **not all namespaces**; a missing styled Question is not replaced with a neutral one. All three reads are provider-free and never synthesize a missing question. The selected format belongs to presentation/grading **after** retrieval, not to stored question identity; callers choose one allowed format for the returned type. The consumer owns repetition avoidance and presentation timing; no attempt history or question scheduler in the library.
- **Delete/update boundary:** `delete_question(id)` returns whether a record existed and was removed; deleting its Word/Sense or Style also removes dependent questions through referential integrity, without turning them into neutral questions. Do **not** add `update_question` merely for CRUD symmetry: Question is a generated artifact, not a user-authored Style. To reject one, delete it and explicitly generate a new Question; each normal generation call already appends new ones. No separate `create_question` for manual authoring is required in this contract. Updating Style voice/diction leaves previously saved Question artifacts alone.
- **Stored shape and trust boundary:** Logically a stored Question needs ID, owner sense ID, nullable `style_id`, type and type-specific payload: `content` (string or structured dialogue), correct-answer material (for `word_to_definition`, its equivalent saved definition alternatives), K distractors and per-choice explanations. This is **one artifact, not a frozen four-option presentation**. The Question's namespace is part of its identity and of sense-scoped retrieval; its saved answer/content is a snapshot, not a pointer to whichever definition happens to be returned on a later read. Do not store `render_format`, `difficulty_level`, exposure/assessment state, shuffled option order, partial rubric score or feedback as Question identity. `get`/`list`/`retrieve` return the **full artifact to the trusted consumer server**, including answers and explanations. The consumer must not forward those secrets to learners before grading; it chooses three distractors from K and shuffles the displayed options. Each stored option needs an answerable identity independent of its shuffled position, so `grade_answer` can compare the selected option against the **authoritative saved question**, not a client-claimed answer key. No in-library render/reveal/attempt state is needed; the consumer owns UI wording, answer hiding and post-answer explanation timing. The exact JSON/DB representation and opaque option-ID encoding are implementation choices, not a second product workflow.
- **Grade:** `grade_answer` loads the authoritative Question **including its stored `style_id`** by ID and uses its type plus the chosen **allowed** format; the caller does not supply another Style to change its answer. For `single_choice`, compare the selected saved option identity in code; return `correct` with the target sense ID or `incorrect` with null, without a model call. For `single_word`, use the saved-answer fast path or the agreed single Jev request (2 Noul + 1 Choice), including correct external senses or correct-but-unresolved null. For `word_to_definition / short_answer`, use one Jev Choice over all stored senses of the displayed Word, including neutral `no_sense`; an accurate learner definition need not match the Question's Style wording. For `word_to_usage / short_answer`, judge the required Word's use as `correct`/`incorrect`/`typo` in its intended sense without requiring the learner to write in that Style. Text grading returns exactly the two fields specified above, without answer-specific explanation; no free-text partial credit, rubric feedback or `pending` score. The consumer owns mastery updates. Invalid type/format/answer or provider errors are errors, not incorrect learner answers; a retrieval miss alone is `None`/`[]`.
- **Minimal internal organization:** Keep a direct orchestration path from the public API to question generation/storage/grading. The final target layout below places seven explicit type-specific generation branches/functions in `questions/generate.py`, validation in `questions/schemas.py`, grading in `questions/grade.py`, and saved-artifact SQL in `db/questions.py`; it does **not** require seven plugin modules or a repository class. Reuse the project's real provider and database seams, but **remove the old plugin registry, engine/factory split, per-call forwarding QuestionService, dynamic capability descriptors, `QuestionContext` capability bag, `prepare`/demand/report, topic-derived distractor provider, exposure/flashcard type, legacy difficulty levels, `text_span`/`free_text` render kinds and per-type plugin graders**. A flashcard, if a consumer wants one, is a Word/Sense display outside the question taxonomy. No compatibility adapter or migration is needed solely to preserve the old generated-question payloads (compatibility decision above).

**Current Question files and why the replacement is smaller (scout evidence, not extra product APIs):** `questions/service.py` forwards `prepare`/reads/evaluation; `factory.py` assembles reader and worker engine variants; `engine.py` dispatches through a registry and makes a context bag; `base.py` declares plugin protocols, demand/query carriers and registration; `questions/__init__.py` imports plugins for registration as a side effect. `questions/plugins/{definition_mcq,contextual_mcq,cloze,use_in_sentence,flashcard}.py` each owns old `prepare`/`retrieve`/`grade`; `plugins/_shared.py` assembles pre-shuffled MCQ options, exposure questions and blanks. `distractors.py` and `dedup.py` synthesize/fold distractors from topics and other old paths. `render.py` builds old render/grading/reveal contracts. `types.py` holds both the old public and internal DTOs, including difficulty, render kinds and `PrepareDemand`; `schemas.py` validates outputs of the old plugins. `scoring.py` currently grades selected **positions** in a pre-shuffled four-option list, matches old text-span accepted forms, or calls an LLM rubric returning score/feedback/`pending`. None is the new answer-by-saved-option-identity, saved-surface/one-Jev-request, no-`pending` grading contract. `lexi_ai/db/queries/question.py` and its payload/schema must also be rebuilt for new append-on-generate artifacts and nullable `style_id`; the DB location is separate from the plugin tree, not evidence that the plugin layering is needed. Remove the **old** roles and add only the explicit per-type generation, saved artifact/repository and actual grading paths required by the seven decided types; do not keep `scoring.py`'s position/rubric logic, a dormant reader engine, or the flashcard under new filenames.

**Status:** Question *product and module architecture* are settled; implementation is not done. Write generation system prompts at implementation time, including the remaining exact Jev wording for `word_to_usage / short_answer`; adapt storage, tests, examples and public docs to this contract rather than treating existing five-plugin tests as the target. Do not reopen the seven types, 12 format pairs or CRUD boundary just because the current engine has different abstractions.

### One public search — generated Words plus optionally available source entries

- **One API, two result groups — decided:** `search(query, include_available=False)` searches generated Lexi-AI Words; when `include_available=True`, the same call also returns Cambridge entries available to request. Expose source-neutral groups/handles such as `words` (existing generated Words) and `available` (not-yet-generated entries with an opaque `available_id`), not two public search methods or a mixed result that makes callers infer which ID to pass where. A consumer can display an add-to-deck/lookup action on `words` and a request action on each `available` result. Do not expose the names Cambridge/WordNet, their IDs, source definitions or raw provenance through the public search, generation or Word read model; keep source metadata internally for generation and traceability. The public `generate(available_id, style=None)` resolves the handle to a Cambridge entry ID internally and optionally creates/reuses that Word's Style content **after** neutral exists, as detailed above. The current public `Lexicon.search()`/`SearchResult` and source-specific arguments describe the **old implementation**, not this contract.
- **Generated-Word group — decided:** Search **only Words with `generation_state="done"`**, including those originally seeded through relations or generated from another Cambridge entry; return Word IDs, not reference suggestions or unfinished/error stubs. Match the user's surface string against lemma, alias, sense forms and explicitly licensed sense patterns. Rank **exact lemma → exact alias → exact sense form → fully matched licensed pattern → prefix → bounded fuzzy**, with stable ordering, matched-surface/match-kind metadata and deduplication by Word ID. Fixed words/particle positions and whole-expression pattern matching are required; `took it off` may match a transitive pattern of `take off`, but `took it` must not match it by deleting `off`. Prefix/fuzzy are suggestions, never identity merges or correctness verdicts; exact `glitter` must rank before fuzzy `glisten`. Query is lexical surface text, not definition/semantic search. Detailed indexes, fuzzy bounds, caps and collisions remain implementation/tuning work, not another product decision.
- **Available-entry group — decided:** Search Cambridge entries by the user query, returning only source-neutral presentation information and an opaque handle for each entry **not associated with a `done` Word**. Hide only consumed IDs whose Word is `done`; pending/error work does not remove the request action. After successful generation, that entry disappears from `available` and its generated Word is returned in `words`. Persist the entry-to-Word association independently of optional per-sense citations; allow multiple Cambridge IDs to point to the same Word so generating a second matching entry cannot make the first reappear. Distinct Cambridge entries may have the same display and remain distinct handles until consumed. Do not offer WordNet-only candidates as requestable entries. If Cambridge search finds nothing, there is no requestable handle and the user must edit the query; `generate()` does not accept the raw query or try to rescue it by searching. Complex/inflected query coverage is limited to what search actually supports; no guarantee that every non-citation surface finds a Cambridge row. The Cambridge database stays read-only.

**Word-type survey informing both result groups (current code and read-only reference data, not a new algorithm):**

- The generated Word schema uses five `entry_type`s: `word`, `phrasal_verb`, `idiom`, `phrase`, `expression` (`lexi_ai/vocab.py`). The mounted Cambridge dataset contains respectively **62,566 / 2,797 / 7,469 / 3,063 / 37,193** rows of these types (113,088 total). `Word` in the redesigned model is one vocabulary item of **any** of these shapes, not necessarily one token. A single Word can also have senses with different POS; aliases are word-level, forms are sense-level.
- Read actual Cambridge displays before designing a matcher: `add (something) up` (optional object/separable particle), `put up with something/someone` (fixed particle order + slot), `book in/into sth` (alternative preposition), `play someone/something off against someone/something` (multiple slots), `all's well that ends well` (apostrophe), `20/20 vision` (slash is literal, **not** an alternative), and `someone's answer to someone/something` (possessive + slots). In the mounted dataset, **537** phrasal-verb rows contain `/` and **267** contain `(`; even slash/parenthesis expansion must be parsed by structure, never applied to every punctuation mark. Some headwords are acronyms, numeric expressions, hyphenated forms or long fixed idioms. Short inputs must not be forced onto a longer construction missing a required particle (e.g. `took it` is not evidence for `take off`).
- Cambridge also has **5,121** `word_alternatives` records (`arrow`, `abbreviation`, `UK spelling`, `another word`, `short form`, `another spelling`) and **19,672** sense rows with an inline `phrase_title`; inline phrases may also have standalone `words` rows or be orphaned (`lexi_ai/dictionary/phrases.py`). Neither a cross-reference arrow nor a phrase title is automatically an accepted alias of its host Word. Multiple Cambridge IDs can share one display form. Its current exact-search surface index covers slug/display and a narrow someone/something slot alternation; its fuzzy search uses `SequenceMatcher` over surface keys with a 0.6 cutoff, **not** general phrasal-verb morphology, object insertion, aliases or form lookup (`lexi_ai/providers/references/cambridge.py`).
- WordNet is a **generation-only supplemental reference**: `WordNetSource.lookup()` substitutes underscores for spaces and returns synsets/lemmas, not Cambridge entry IDs; its coverage is uneven (`take_off` returns synsets, `put_up_with` can return none). WordNet must not appear as a separate public result or a prerequisite for generating a selected Cambridge entry. The mounted Cambridge DB has no standalone display `take off`, although its slug `take-off` lets the current exact resolver find the row displayed as `take something off`; do not mistake display absence for no Cambridge match. The read-only Cambridge DB must remain untouched; any new index/derived view belongs outside it.
- The generated dictionary currently has indexed `words.match_key` and `word_aliases.alias_match_key`, with aliases for spelling, spacing, hyphenation, particle/preposition/optional-element/placeholder variations, etc. `senses.forms` records per-sense inflections (`past`, `ing`, `plural`, etc.), but current `resolve_key()` searches only headword/alias, **not forms**. Current public search retrieves generated words only by Cambridge provenance and therefore misses independently generated Words. `match_key()` preserves diacritics and meaningful punctuation, collapses whitespace and currently folds natural `someone`/`something` into placeholder keys; the new identity contract must distinguish literal text from marked slots. It does not parse arbitrary slots, separable constructions, or validate that a surface form fits a particular sense. Those are implementation gaps in the unified search's `words` and `available` paths, not evidence that current character similarity implements the proposed matcher.

### Shared Jev/LLM decision adapter — decided direction

- Jev is the primary decision model. Introduce an abstract decision-model contract for a `state` and its typed question set (including multiple questions in one request), with Jev and an LLM adapter producing the **same consumer-facing typed answers and option keys**. When **applicable** Jev Choice confidence falls below 0.7, convert the **whole Jev decision request** to a single LLM fallback request; do not hand-author a separate LLM prompt or request for each Jev task/question. An eagerly asked `matched_sense` Choice whose answer is discarded for `incorrect`/`typo` is **not applicable** and must not trigger fallback on its own. Preserve the original decision semantics, including Noul yes/no and Choice criteria; map model-selected option keys to internal sense IDs in code, not in the model output.
- The WSD-specific system/user fallback prompts previously recorded here are **superseded** by this generic adapter. The exact WSD Jev state template and static question above remain decided. **All Jev thresholds, including WSD Choice acceptance/fallback and Noul yes-probability, are now 0.7**; retain the distinction between what those two measures mean. How multi-question confidence triggers fallback and how provider-specific confidence is represented need to be designed without fabricating Jev-calibrated confidence for the LLM.
- Implementation reference only: [TypeSafe System One adapter for Python](https://github.com/typesafe-ai/system-one-adapter-python). **Do not clone or inspect this repository during this note-taking step**; consult it later when designing the converter.

The current WSD prompts, source/target-hash invalidation and read-model paths assume a single `sense.definition`. Reconcile them with multiple **unordered, equal-standing** neutral `definitions` rows; where a task needs a single meaning anchor, **select one explicitly** and keep that selection stable within the operation or saved artifact, never use an implicit “first” DB row. Do not treat a definition variant as a separate sense or change the agreed Jev/LLM choice format. The numeric `1..N` WSD Choice indices enumerate **candidate senses** in the selected candidate list, not stored definitions in a canonical order; if candidate criteria mention several equivalent definitions, they still map to that one sense ID. Similarly, Style namespaces, definition-backed assets and Question generation/grading must stop assuming there is one stored definition per sense. Definition/Example tables use `content` rather than `text` and have no definition/example order; the Sense order and question distractor-confusability order are distinct concepts. This is cross-cutting implementation follow-through, not a newly reopened WSD product decision.

### WSD relation taxonomy and implementation audit

- **Final relation taxonomy:** Sense-level `synonym`, `antonym`, `hypernym`, `hyponym`, `meronym`, and `holonym` have distinct lexical meanings and normally compare senses of the same POS. The removed `see_also` is the explicit cross-POS example. Only word-level `word_family`, `confused_with` and system-derived `part_of_phrasal_family` remain; none enter WSD. Cross-POS word-family links are not a reason to keep cross-POS WSD. Do not reintroduce removed catch-alls or add relation types merely because the directed pairs are inverses.
- **Prompt data currently missing:** `pending_relations()` selects source definition/POS, relation, gloss and target word ID, but not **source word** or **target word text**. Both are required by the agreed Jev/LLM state template; add the appropriate joins/projections before implementation (`lexi_ai/db/queries/sense_relation.py:43-93`, `lexi_ai/models.py:351-363`).
- **Candidate ordering hazard:** `pending_relations()` applies `LIMIT WSD_CANDIDATE_CAP` to all target senses *before* the current Python POS filter. With strict POS, an eligible matching-POS sense beyond the first 12 would be missed and the edge could be wrongly marked unresolvable. Filter by the source POS **in the query before limiting**, with stable order, then map indices `1..N` to exactly those rows.
- **Stale-hash queue mismatch:** `sense_relation_view()` renders a stale resolved target as `pending` when its definition hash changes (`lexi_ai/db/mappers.py:53-85`), but `pending_relations()` selects only `to_sense_id IS NULL` (`lexi_ai/db/queries/sense_relation.py:55-59`). Such an edge can appear pending to the consumer without being picked up by `resolve_relations()`. Ensure a stale link becomes genuinely eligible again, without trusting its old resolution; preserve target-hash invalidation.
- **Missing-provider signal:** The current resolver returns `[]` when no judge is configured (`lexi_ai/dictionary/enrich.py:95-101`), indistinguishable from no eligible work. Under the explicit Jev-first job, report missing required provider configuration visibly rather than treating it as an empty queue.
- **Status:** WSD product design is settled (including the global 0.7 Jev threshold, strict POS, no `see_also`, per-link Jev and optional per-link LLM fallback, internally parallel `resolve_relations(batch_size)`), but implementation and verification are **not done**. Existing batch-judge prompts/tests and the cross-POS test must be replaced or updated; do not report WSD finished solely because the decisions are recorded here.

- `references/cambridge.py` reads the separate Cambridge database only: search, selected-ID fetch and phrase evidence. `references/wordnet.py` supplies optional supporting evidence for Word generation. Their names, raw IDs, definitions and provenance never cross into public models/results. Do not build an extra `ReferenceLoader`/evidence-bundle layer just to connect these two files. `db/` means **only the writable generated dictionary DB**, even though Cambridge itself is SQLite.
- `words/search.py` owns the single search's two groups and lexical ranking; `words/generate.py` owns selected-entry → one neutral Word, reuse of an already-done Word, evidence/LLM validation and optional subsequent Style generation. `words/schemas.py` validates Word-generation output, not public read models. No `words/read.py`: `api.py` can call `db/read.py` directly for provider-free Word/Sense views. No `words/styles.py`, `words/relations.py`, or `words/topics.py`: Style is an independent content namespace, WSD is an explicit job, and Topic membership/curation fits the Word DB operations.
- `styles.py` owns Style create/list/get/update/delete and generate-if-missing definitions/examples for a **complete Word–Style pair**; it uses `db/content.py` for atomic storage. Style also namespaces Questions but must not generate them or change shared lexical facts. `relations.py` owns only the explicit `resolve_relations(batch_size)` job: per-link Jev decision and optional fallback, independent per-link error isolation and within-call parallelism; never an inbound hook of Word generation. `translation.py` owns `translate_text` and cache management, with cache SQL in `db/translations.py`, not mixed into the provider call.
- `questions/schemas.py` validates the seven type-specific output shapes, whole batches and saved artifacts. `questions/generate.py` has seven **explicit functions/branches**, not seven plugin classes/files: one request produces `count` **new** same-type artifacts, then one atomic insert of the batch through `db/questions.py`. `questions/grade.py` loads the saved artifact, checks allowed format, grades choice by saved option identity in code and delegates agreed text decisions to `decision.py`. `questions/__init__.py` must not register or eagerly import plugins. No Question engine, factory, `prepare`, render/reveal or topic-derived distractor service.
- `db/schema.py` contains generated-DB ORM/FKs/indexes; `db/session.py` owns engine/session and explicit transaction boundaries, without a prewired repository graph. `db/words.py` groups Word/Sense/alias/form/topic, search SQL and the internal many-Cambridge-entry-IDs-to-one-Word association; `db/read.py` queries and assembles detached views **inside the session** (no extra `mappers.py`) and filters internal provenance. `db/content.py` groups Style metadata and neutral/styled Definition/Example persistence; `db/relations.py` holds pending/candidate SQL, strict POS filtering before cap, verdicts and stale-link invalidation; `db/questions.py` holds artifact append/get/list/random retrieval/delete; `db/translations.py` holds text-hash cache lookup/insert/management. These are cohesive SQL groups/functions receiving a shared session, **not one repository class per table**. Multi-step Word/Style/Question writes remain atomic, and FK cascades must not relabel styled rows as neutral.
- `prompts/` retains only templates actually used by the new use cases; do not preserve the old provider-oriented tree or prompts for removed paths. `migrations/versions/` contains one fresh final baseline matching `db/schema.py`; the Cambridge reference DB and its history are not migrated by it. No automatic model/prompt provenance columns.

### Concrete call paths to preserve

1. `search(query, include_available=False)`: `api.py → words/search.py → db/words.py`; if requested, also `references/cambridge.py`. Search only `done` generated Words; `available` uses an opaque, source-neutral handle and excludes only source IDs already associated with a `done` Word. Matching/ranking follows the search contract above, not fuzzy identity merging.
2. `generate(available_id, style=None)`: `api.py → words/generate.py → references/cambridge.py` by selected ID plus optional `references/wordnet.py → llm.py → db/words.py` and `db/content.py` (including half-edge writes via `db/relations.py`) in a single neutral publish. If Style is requested, neutral exists first, then `styles.py → db/content.py` creates the complete styled content **only if missing**. No Question generation or inbound WSD hook.
3. `get_word(..., style)`: `api.py → db/read.py`; detached, provider-free and namespace-exact. An incomplete/missing styled Word returns `None`, not neutral fallback. Sense display order is distinct from unordered Definition/Example rows.
4. `generate_questions(sense_id, question_type, count, *, distractor_count, style=None)`: `api.py → questions/generate.py → llm.py → db/questions.py`. Exactly one LLM generation request adds N new validated, saved artifacts for one type/namespace; existing artifacts are never a generation cache hit. Get/list/retrieve call DB only. `grade_answer(id, format, answer)` reads the authoritative saved artifact via `db/questions.py`, then `questions/grade.py` handles choice locally or calls the one shared `decision.py` for text grading.
5. `resolve_relations(batch_size)`: `api.py → relations.py → db/relations.py → decision.py` for each eligible edge, with strict same-POS candidate selection before the cap, per-edge decision/fallback and separate error handling. No cross-call queue or lock.
6. `translate_text(content, target_language)`: `api.py → translation.py → db/translations.py`; a miss invokes `llm.py` and stores text under `(hash of the exact text sent to the translator, target_language)`. No source-row resolver, TTS/file asset, model ID or prompt version in the key.

### Rewrite and verification rules

- Rebuild responsibilities, **do not mechanically move files**: current `dictionary/*`/`providers/generate.py`/`db/queries/*` become direct Word/search/read/DB operations; `themes.py` becomes Style metadata and whole-Word content, not an overlay; old `questions/{base,engine,factory,service,plugins,render,scoring}.py` are replaced by the explicit artifact flow; `assets.py`/file storage/GC/TTS are deleted in favor of text translation cache. `dictionary/enrich.py` loses `add_examples` and inbound resolution; `models.py` sheds old fence/batch/internal-source carriers. Preserve real transaction and provider-injection test seams, not the old wrapper graph.
- Keep the feature boundary pragmatic: only `words/` and `questions/` need **business packages** because each contains multiple substantial, independently evolving flows; `references/` groups two read-only sources. Style, WSD and translation stay root modules. `db/` has several files because read projection, Word publish/search, content namespaces, WSD, artifacts and translation cache have genuinely different SQL concerns, **not** because every table needs a repository. Avoid both previous extremes: a giant root/`db/words.py` and a package/adapter per product noun.
- Rewrite tests around behavior rather than moving the old plugin/lock/TTS tests: search ranking and source-neutral output, selected-ID association, Cambridge read-only, Word/Style full atomic publish and no neutral fallback, one-request N-question append, saved-artifact grading, strict-POS/per-edge WSD, exact-text translation cache, FK cascades and detached reads. Keep meaningful SQLite/Postgres rollback and baseline-migration checks, including fresh Postgres upgrade, drift, downgrade/re-upgrade and non-default schema. Public/import tests must prevent source provenance and ORM/provider side effects in public models and prevent model calls on reads. Update examples/docs and stale import-linter contracts to this layout; do not create a new layer merely to make an import rule pass.

## Duplication and avoidable complexity

### 1. Two level-1 question types produce essentially the same question

- **Evidence:** `lexi_ai/questions/plugins/definition_mcq.py:48-64` and the level-1 branch of `lexi_ai/questions/plugins/contextual_mcq.py:58-84` both build a `Which word means: ...` stem, request the same kind of distractors, and call `_mcq_question`. Their `type_id` and shuffle seeds differ; contextual MCQ level 2 is genuinely different.
- **Impact:** Two persisted question types and two preparation paths for effectively the same level-1 learning activity.
- **Later decision supersedes this question:** The agreed `definition_to_word` type uses AI-authored distractors and supports `single_choice` and `single_word`; the complete seven-type contract is recorded above. Current duplicated level-1 behavior is implementation evidence, not a reason to preserve both old type IDs.

### 2. Repeated plugin dispatch boilerplate

- **Evidence:** `prepare` has the same implementation in `lexi_ai/questions/plugins/contextual_mcq.py:41-56` and `lexi_ai/questions/plugins/cloze.py:38-53`. The `retrieve` flow is repeated in those plugins and `lexi_ai/questions/plugins/use_in_sentence.py:86-96`.
- **Impact:** Changes to demand handling or retrieval checks must be synchronized across plugins.
- **Superseded direction:** Do not refactor the duplicated `prepare` methods into another plugin framework. The settled replacement question module above removes plugin dispatch and `prepare`; keep type-specific generation explicit and share only the genuinely common storage/grading behavior.

### 3. A word is marked `done` twice in one publish transaction

- **Evidence:** `WordQueries.upsert_core()` sets `word.status = "done"` in `lexi_ai/db/queries/word.py:74-92`; `GenerationWriter.publish()` then calls `mark_done()` for every word in `lexi_ai/dictionary/writer.py:61-73`, issuing another UPDATE through `lexi_ai/db/queries/word.py:147-150`.
- **Impact:** Redundant writes per generated unit.
- **Direction:** Verify transaction and error-state invariants, then keep one authoritative transition to `done`.

### 4. Batch reads fan out to per-ID sessions and queries

- **Evidence:** `DictionaryService.entries()` calls `entry()` for each ID and re-resolves the same theme for every item when a theme is supplied; `statuses()` calls `status()` for each ID (`lexi_ai/dictionary/read.py:53-62,78-89,91-107,121-134`). Concurrency is limited to 16, but the query/session count still scales with the input size.
- **Impact:** Unnecessary database round trips for larger batches; themed reads additionally repeat theme resolution.
- **Superseded direction:** The convenience `get_many`/`entries` wrapper is already decided for removal; do not redesign its theme-resolution or batch fan-out as a new feature. For any genuinely retained batch DB read, resolve a requested **Style** appropriately without resurrecting the removed per-item wrapper. This row documents cost in the current code, not an open Style-product decision.

### 5. The reader question engine exists, but public reads always select the worker engine

- **Evidence:** Every `Lexicon` question method uses `_questions(providers=True)` (`lexi_ai/lexicon.py:518-558`). `engine(providers=False)` in `lexi_ai/questions/factory.py:37-65` is called only by a direct test (`tests/test_api.py:925-935`). The worker factory requests separate question and judge LLM clients via `lexi_ai/providers/registry.py:60-75` when configured, even if the first public operation is only a read.
- **Impact:** An extra engine path to maintain, and provider initialization on a read-only question path when credentials exist.
- **Superseded choice:** Remove both reader/worker engine variants and make the new `get`/`list`/`retrieve` methods provider-free by construction. Jev-backed grading remains an explicit operation; the legacy rubric grader is not a contract to preserve.

## OpenAI SDK cleanup: agreed direction

At scout time the project used OpenAI Python SDK **2.44.0** (`uv.lock`). Native `chat.completions.parse(..., response_format=PydanticModel)` and request timeout/token limits were in use. The old audio path used `audio.speech.create()`, but **TTS is now explicitly removed**, so its SDK path is not a retained capability. The following structured-output decisions supersede the earlier idea of keeping a tool-calling fallback for proxies.

### 10. Remove function-calling structured output completely — decided

- **Target:** One structured-output path only: the SDK's `chat.completions.parse()` with a Pydantic `response_format`. No tool-calling mode, automatic fallback, alternate parsing route, or proxy-specific schema rewrite.
- **Remove end to end:** `OpenAIStructuredLLM`'s method switch, `_parse_via_tool()`, `drop_nullable_unions()`, tool-call parsing/diagnostic helpers used only by that branch, and the `pydantic_function_tool`/forced `tool_choice` integration in `lexi_ai/providers/seam.py`. Remove `llm_structured_method` from `lexi_ai/config.py`, `_llm_for_method()` and method-specific client cache from `lexi_ai/providers/generate.py`, and `structured_method` arguments threaded through `lexi_ai/dictionary/generate.py` and public `Lexicon.generate()` / `generate_fenced()` in `lexi_ai/lexicon.py` if those arguments have no other purpose. Search for remaining references before declaring completion.
- **Examples and tests:** Remove the `function_calling` setting and default override from `examples/.env.example` and `examples/_common.py`; rewrite the proxy guidance in `examples/README.md`. Remove tool-only tests in `tests/test_structured_tool_schema.py` and the function-calling cases in `tests/test_llm_spend_bounds.py` and `tests/test_generation.py`. Retain or add tests for the sole native-parse path, Pydantic validation, request limits, and explicit failures.
- **Comments and docs:** Delete or rewrite all stale comments/docstrings describing forced tools, nullable-union rewrites, method selection, or a proxy fallback throughout source, examples, and tests. Do not leave a compatibility knob or explanatory text implying the removed mode still exists.
- **Accepted consequence:** This intentionally breaks callers of `structured_method` and environments that relied on `LEXI_LLM_STRUCTURED_METHOD=function_calling`. A proxy that cannot satisfy native strict structured output must fail visibly; do **not** silently use tool calling, loose JSON, or another proxy-specific workaround. A configurable `base_url` can remain for endpoints that implement the required native contract; it does not imply fallback support. Update examples accordingly rather than pretending the old proxy setup still works.

### 11. Use one retry layer — decided

- **Evidence:** `ainvoke_structured()` in `lexi_ai/providers/seam.py:304-348` makes up to three outer attempts while `AsyncOpenAI` defaults to two retries (three HTTP attempts) for connection errors/timeouts and selected statuses. A transient failure can therefore result in **up to nine HTTP attempts** before the application raises.
- **Direction:** Let the SDK own transport/HTTP retries and configure **one explicit retry budget** on its client (the SDK default of two retries is the initial baseline). Remove the overlapping production retry/backoff/classification loop and adjust fake-based tests. Preserve validation without retrying schema failures. Keep the existing request timeout and token ceiling; do not add a separate application-level retry for a proxy-specific status.
- **Verification:** Test transport failure count and latency budget using an SDK-level fake/transport, not only a fake `StructuredLLM` that bypasses the SDK's internal retries.

### 12. Own, reuse, and close SDK clients — decided

- **Evidence:** `Lexicon.close()` currently disposes only the database engine (`lexi_ai/lexicon.py:175-177`). Clients were created in `lexi_ai/providers/seam.py:194-203` and the **now-removed target** `lexi_ai/providers/tts.py:71-78`; `ProviderRegistry.questions_llm()` and `judge_llm()` each build a new structured client (`lexi_ai/providers/registry.py:60-75`). The generator also caches clients by output method (`lexi_ai/providers/generate.py:70-85`).
- **Direction:** Reuse an SDK client for calls sharing credentials/base URL, choose model/schema per request, and avoid constructing separate clients just for question generation versus judging. **Remove the separate TTS client and its wiring rather than managing its lifecycle.** Close every retained **owned** async SDK client as part of `Lexicon.close()` (or an equivalent explicit lifecycle); do not close caller-injected clients unless ownership is explicitly transferred. Keep fake injection possible.
- **Verification:** Cover repeat calls, different model overrides, and close-once behavior for owned versus injected clients.

### 13. Use the SDK's typed `reasoning_effort` argument — decided

- **Evidence:** `lexi_ai/providers/seam.py:219-235` currently passes `reasoning_effort` via `extra_body` and claims it is not a first-class SDK parameter. The installed SDK 2.44.0 exposes it directly on both `chat.completions.create()` and `.parse()`.
- **Direction:** Pass it as a standard request argument when configured; remove the obsolete comment and `_extra()` shim if nothing else uses it. Keep omission when unset. A model/endpoint that rejects the parameter should fail explicitly rather than trigger another compatibility mode.

### Keep these project-owned rules

- `guarded_messages()` and its untrusted-input boundary: prompt/data safety is not supplied by the SDK.
- The `StructuredLLM` injection seam if it continues to make tests independent of network calls; it must no longer imply a second wire protocol or duplicate SDK retries.
- A correct translation-cache identity once chosen, validation of translated data, and the configured timeout/token ceiling: these protect project behavior, not SDK transport behavior. Do **not** retain the old source-row hash verifier automatically if translation switches to a text-addressed cache.
- **Remove** the TTS empty-audio guard and `audio.speech.create()` call along with the TTS feature; being an existing SDK call is not a reason to retain it.

## Residual Clean Architecture audit and naming decision

The old `application` / `domain` / `infrastructure` package layout is gone from active library imports. The main remaining cost is unnecessary indirection in the question flow, not the use of `Service` as a class suffix. These findings are an assessment of the current working tree; they do **not** mandate flattening every boundary.

### 14. Question use cases have an extra forwarding layer — investigate

- **Evidence:** `QuestionService` in `lexi_ai/questions/service.py:44-104` forwards most calls to `QuestionEngine`; `Lexicon._questions()` in `lexi_ai/lexicon.py:192-202` recreates the service wrapper per call over a cached engine and repository.
- **Cost:** To follow a question operation, a reader must cross `Lexicon` → service → engine/plugin or repository even where the service adds no behavior.
- **Replacement decision:** Remove the old forwarding service/engine/plugin chain. The new `grade_answer(question_id, ...)` still loads the authoritative saved question, never trusting a client-supplied answer key. Unlike the old answer-free `PresentedQuestion`, the public Question read is deliberately the **full artifact for a trusted consumer server**; the consumer hides answers before showing the learner. Do not keep `render`/`reveal` solely to mimic the old boundary.

### 15. An internal question demand preserves unused configurability — investigate

- **Evidence:** Public `PrepareDemand` is mapped to internal `QuestionDemand(expected_count=1)` in `lexi_ai/questions/service.py:30-41`. `expected_count` is checked for positivity in the engine/plugins (`lexi_ai/questions/engine.py:62-94` and plugin `prepare` methods), but each applicable plugin still produces at most one question, even when an internal caller passes a larger count.
- **Replacement decision:** `generate_questions(..., count, distractor_count)` genuinely generates `count` distinct Question artifacts with one LLM request for one sense/type; the old `QuestionDemand`/`PrepareDemand`, aggregate `PrepareReport` and `expected_count=1` translation are deleted, not renamed.

### 16. Importing the supposedly isolated question contract has plugin side effects — investigate

- **Evidence:** `lexi_ai/questions/__init__.py:8-17` imports all built-in plugins to register them. A runtime probe confirmed that `import lexi_ai.questions.types` also loads `lexi_ai.questions.plugins`, `lexi_ai.providers.seam`, and `lexi_ai.models` through the package initializer. `tests/test_contract_imports.py:8-21` checks that DB/SQLAlchemy stay unloaded but does not check plugin/provider imports.
- **Replacement decision:** The new module has no plugin registry or registration import side effects. Do not move the old registry to another bootstrap location: delete that indirection and use explicit type-specific generation paths.

### 17. A relation mixin and architecture checks still describe removed ports — low priority

- **Evidence:** `lexi_ai/db/queries/sense_relation.py:1-5,28` justifies `SenseRelationResolutionMixin` in terms of a `SenseQueries` port that no longer exists; the mixin is inherited in `lexi_ai/db/queries/sense.py:49`. `pyproject.toml:59-75,101-114,137-148,175-183` still discusses removed layered packages. `tests/test_assets.py:986-992` claims an `AssetStore` Protocol, whereas `AssetService` now accepts `AssetRepository` (`lexi_ai/assets.py:23-32`).
- **Direction:** Fix stale claims and test names first. The mixin holds real relation-resolution logic; moving or merging that logic requires a separate cohesion review, not deletion based on terminology.

### 18. Keep useful transaction and read-model boundaries — decided

- `SqlAlchemyUnitOfWork` currently gives multi-step writes a shared session and explicit commit boundary (`lexi_ai/db/session.py:103-175`); deleting **the transaction boundary** merely because the old architecture used UoW is not justified. The target `db/session.py` may implement that boundary without preserving the current class/repository graph.
- `lexi_ai/db/mappers.py` currently detaches read models from ORM rows, allowing results to survive a closed async session. Preserve **that behavior**, but the selected target places query and assembly together in `db/read.py`, without a separate `mappers.py`. The provider test seam remains useful for hermetic tests.
- The **current** Asset and Question repositories use independent session scopes where their workflows differ. That is not by itself a correctness bug. With TTS/file GC removed and Questions rebuilt, re-evaluate only the transaction scopes still doing real work; do not keep old listeners/locks to preserve the pattern.

### 19. Do not mass-rename `*Service` classes — decided

- A `Service` suffix is not itself a Clean Architecture remnant; this scout finding was **not** an instruction to preserve old classes. The selected rewrite puts genuine orchestration in `words/generate.py`, `words/search.py`, `styles.py`, `relations.py` and `translation.py`, without a mandatory `*Service` class or forwarding layer. Old `AssetService`/`EnrichmentService` responsibilities tied to TTS, `add_examples` and inbound resolution are removed.
- Earlier permission to retain names like `DictionaryService`, `SearchService` and `TagService` for consistency is superseded **as an organizational recommendation** by the target structure above. It does not weaken the rule that a surviving object must own real behavior/lifecycle, rather than simply forwarding calls.
- The question module replacement above **removes the old forwarding `QuestionService`**; any surviving orchestrator must own real generation/storage/grading work, not simply forward to a renamed engine. This is about responsibility, not the `Service` suffix.
- **Rule:** Remove an unnecessary layer first; rename afterward only if the surviving responsibility demands it. No bulk rename for stylistic purity.

## Exclusions and verification

- Historical migrations and concurrency/transaction/file-GC guards were not originally classified as dead merely because their call sites were narrow. The **later product decisions** explicitly remove TTS and its file-backed GC, cross-call coordination, `add_examples` and proxy-specific function-calling, regardless of whether those paths had callers. Keep legitimate transaction safety for surviving Word/Style/Question/translation writes.
- This scan used source inspection and call-site searches; dynamic use or out-of-repository consumers can invalidate a dead-code candidate.
- At scan time: Ruff passed; import-linter kept **6/6** contracts; pytest reported **559 passed, 13 skipped**. Tests were run against the then-current working tree, not against proposed cleanup changes.

The OpenAI SDK direction in items 10-13, the no-mass-rename/no-forwarding rule in item 19, the compatibility/migration scope, selected-entry generation, consumer-owned concurrency and **target project structure above** are settled directions. `Lexicon` remains a proposed public class name rather than a confirmed naming decision. Client ownership, retry counts, and native-parse-only tests are implementation and verification work within that direction, not topics to reopen.
